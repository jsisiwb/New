# ADR-0051: The novel run is the operator's unit of work; a Postgres-queued runner drives it; live providers are configured by name

- **Status:** Accepted
- **Date:** 2026-09-20
- **Deciders:** engineering agent (product completion)
- **Relates to:** ADR-0012 (rolling-horizon hierarchical planning), ADR-0019 (assisted default mode),
  ADR-0036 (MVP vertical slice), ADR-0044 (modular monolith first), ADR-0046 (chapter production
  implementation), ADR-0047 (Temporal adapter over checkpointed steps), ADR-0048 (atomic lease fencing),
  migration `0019_novel_runs.sql`, `docs/03-story-planning/01-story-planning-architecture.md`,
  `docs/06-system/07-model-gateway.md`

## Context

Every stage the plan describes existed as a proven, replay-tested step — spec interpretation, the bible
commit, arc planning, chapter contracts, drafting, evaluation, revision, extraction, atomic acceptance —
and none of them were connected into the thing the product promises: an operator describes the novel they
want, reads a few story directions, approves one, and the studio writes the whole book.

Three gaps made the product non-functional end to end:

1. **The bible was authored fixture data.** `produceChapter` took a hand-written `StoryBible`; the four
   design prompt families the plan defines for producing one (`character_designer`, `world_builder`,
   `power_system_designer`, `story_architect`) and the `concept_generator` were registered but never
   called. A long story needs the complete bible — every character, secret, world rule, promise and
   season — before chapter 1, or later chapters plan against nothing.
2. **Chapters were started one at a time, by hand, from a fixture arc brief**, and only through a
   Temporal cluster that no local or single-operator deployment has. There was no durable record of
   "this project is being written; chapter k is next; keep going".
3. **No provider an operator actually holds a key for was reachable.** The gateway's `Provider`
   interface was implemented by the replay fixture, a mock, a synthetic simulator and a bespoke local
   bridge. An OpenAI-compatible or Anthropic key had nowhere to go.

Two constraints from the invariants shape the fix. Planned ≠ happened (ADR-0038): a model-generated bible
is PLANNED data and becomes registry rows and a `bible` commit exactly as the fixture one did, never
realized canon. And the chapter loop's guarantees (deterministic step keys, content-addressed artifacts,
winner-only propagation, atomic acceptance, lease fencing) must not be re-implemented in a second, weaker
orchestrator.

## Decision

**1. A `novel_run` row is the operator-facing state machine.** One row per project (`novel_runs`,
migration 0019) records where the novel is: `intake → suggesting → awaiting_approval → planning →
producing → completed`, with `paused`, `needs_attention`, `failed` and `cancelled` as resting states.
`next_chapter`, `target_chapters`, `auto_continue` and `stop_after_chapter` carry the production intent;
`last_error` carries a closed code and an operator-safe message. Every transition appends to
`novel_run_events` (append-only), which is what the UI shows. The chapter and planning JOBS keep their own
`jobs`/`job_steps` checkpoints; the run row says *which* job is next, never *what* it produced.

**2. The bible is generated by the plan's own prompt families and assembled deterministically.**
`suggestConcepts` interprets the intake into the Story Spec and asks `concept_generator` for N distinct
directions (N from the pinned policy's `candidates.concept_candidates`, minimum 2). After approval,
`buildFullBible` calls `character_designer`, `world_builder`, `power_system_designer` and
`story_architect`, then ASSEMBLES the `StoryBible` in code: entity ids derive from stable keys
(`uuidFromKey(project:entity:type:name)`), every model reference resolves against that registry by name,
secrets become propositions with knowledge stances, registers become relationship seeds, world and power
rules become locked facts under a `World rules` term entity, and anything that does not resolve is dropped
rather than invented. The Series Blueprint is validated against `series-blueprint.schema.json` with seasons
normalized so every chapter 1..N belongs to exactly one season. The plan is pinned on the project
(`settings.story_plan` → content-addressed artifact ids) so every chapter job and every process reads the
same bible.

**3. Arcs are planned per season from the blueprint (rolling horizon, ADR-0012).** `produceChapter` takes
an optional `blueprint`; when present the chapter's season decides the arc, `planArcFromBlueprint` runs
once per arc id (checkpointed and reused across chapter jobs through `existingArtifact`), the previous
arc's exit assertions feed the next brief, and the chapter planner is shown the registry WITH ids, the
secrets with their knowers, and the open promises. Project-scoped artifacts (`story_spec`, `arc_plan`) are
read before being regenerated, so a live model is asked once per project, not once per chapter.

**4. A Postgres-queued runner drives runs; Temporal remains the multi-worker chapter orchestrator.**
`canon.claim_novel_run` hands a `planning`/`producing` row to exactly one runner (`FOR UPDATE SKIP LOCKED`
plus a fenced lease renewed on a heartbeat). `advanceNovelRun` performs ONE unit — the plan, or one chapter
through the unchanged `produceChapter` — and reports what happened; the runner loops while it still owns
the run. The API can host the runner inline (`YEONJAE_NOVEL_RUNNER=inline`, the default) so one process is a
complete studio; `@yeonjae/worker start:novel` runs it separately. The chapter-level `target_leases` and
in-transaction fence assertions stay authoritative; this lease only decides who drives the run.

**5. Live providers are configured by variable NAME and fail closed.** `YEONJAE_PROVIDER_MODE=live` with
`YEONJAE_LIVE_PROVIDER` (`openai` | `anthropic`), `YEONJAE_LIVE_API_KEY`, `YEONJAE_LIVE_BASE_URL` and
`YEONJAE_MODEL_{R,P,M,C}` (or `YEONJAE_MODEL_DEFAULT`), plus an optional `YEONJAE_LIVE_FALLBACK_*` provider
at priority 2. The adapters classify every failure, treat a caller abort as cancellation (ADR-0049), bound
the response body, report missing usage as unknown, hold the key in a closure and refuse plaintext HTTP to
a non-loopback host. A missing key or model name is a startup error naming the variable. The resolution
lives in `@yeonjae/gateway` so the API, the worker and the CLI read the same variables the same way.

**6. Live-model outputs are normalized where the fixture never needed it, and validated where it counts.**
Families whose declared output schema describes the COMPLETED document (spec, concept, blueprint, arc,
contract, extraction, patch, comparison, scene draft) are validated once, in the workflow, after the
pins are filled in; the gateway still requires parseable JSON (fence stripping, outermost-object
extraction, bounded repair via `outputMode`). Scene drafts are re-segmented from their own prose when the
model's paragraph table disagrees with it; extractor evidence spans are re-anchored to where their quotes
actually are (a quote absent from the text still fails verification); the L1 ending hook falls back to
the manuscript's verbatim last paragraph when the model paraphrases. None of these change a claim — they
change offsets the model cannot count.

## Alternatives considered

- **Decompose the pipeline into Temporal activities and require Temporal everywhere** — rejected: it
  forks the canon invariants into a second orchestrator (the reason ADR-0047 kept `produceChapter` whole)
  and makes the product unusable without a cluster.
- **Let the model emit the `StoryBible` JSON directly** — rejected: ids, knowledge stances, relationship
  seeds and locked facts would then be model-invented and unverifiable. Assembly in code keeps every id
  derivable and every reference checked.
- **Validate every family's raw output against its full schema at the gateway** — rejected: the schemas
  describe finished envelopes (with `project_id`, pins, call ids); a live model would fail every call for
  fields the workflow adds afterwards. The fixture path never noticed because recordings are complete.
- **A provider-specific SDK per vendor** — rejected: two wire protocols (OpenAI chat completions,
  Anthropic messages) cover every hosted and self-hosted model an operator is likely to configure, and
  the adapter contract forbids SDK types leaving the adapter.

## Consequences

- Positive: the product loop works end to end from one process with one key; the full bible exists before
  chapter 1; production continues across chapters and survives restarts; every stage remains
  checkpointed, audited and budgeted through the existing gateway.
- Negative / limits: the bible-assembly heuristics (name resolution, register levels, attribute slugs)
  are deterministic but simple; a model that names an entity inconsistently loses that reference rather
  than gaining an invented one. `needs_attention` still requires an operator; autopilot never overrides
  a quality gate. The inline runner is single-process; multi-process deployments use `start:novel`
  workers (the queue is safe for several).
- Follow-ups: record the live-provider validation run in `docs/08-delivery/09-progress.md` when it has
  actually happened; the traceability matrix gains the novel-run lifecycle (FR-1.x intake → production).
